# Nadi Payment Provider Pilot Receipt Contract

Phase 1 v142 adds the Payment Provider Pilot Receipt Contract after the Gateway Decision and Webhook Drill. The purpose is to turn a provider decision into exact backend-owned receipt fields before the first paid pilot is trusted. The room keeps the payment pilot deliberately narrow: checkout creation, signed webhook verification, idempotency replay, entitlement mutation, invoice issue, refund or cancellation, settlement reconciliation, support repair, and incident closeout must each produce a receipt that can be replayed without relying on browser-local state.

The contract is provider-neutral. It can describe a Razorpay-style, Cashfree-style, Stripe-style, or manual founder-beta posture, but it does not claim that any provider has already been integrated. A launch-ready version still needs backend checkout creation, official provider credentials, webhook signature validation, timestamp tolerance, schema validation, idempotency keys, immutable event IDs, entitlement joins, invoice references, refund references, settlement references, support case IDs, and incident closeout IDs.

Phase 1 v143 adds the Pilot Receipt Vault after this contract. The contract names the fields; the vault decides whether those fields are stored append-only, replayable into access state, joined to invoice/refund and settlement ledgers, available to support through redacted lookup, exportable for review, and protected by incident freeze rules.

Phase 1 v153 adds the Payment Provider Twin inside the same room. The twin is a provider-neutral rehearsal layer that mirrors checkout creation, signed webhook verification, duplicate event handling, entitlement projection, invoice/tax proof, refund or cancellation reversal, settlement variance, support repair, and incident freeze behavior before any live paid investor is exposed. It produces a twin run ID, scenario IDs, synthetic event hashes, expected and actual backend states, rollback references, owner signoff, and replay timestamps so the founder can compare the planned payment contract against production behavior.

Phase 1 v303 adds Production Provider Deployment Receipts inside the same room. The deploy receipts connect the provider twin to the first real production gate: provider account decision, server-only secret references, webhook endpoint deployment, settlement import checks, rollback receipts, monitor signals, owner acknowledgements, support closeout, no-go rules, and a blocked-data scan. This keeps the payment launch from moving on a provider demo alone.

The blocker logic is intentionally strict. Missing signed webhook proof, weak idempotency, manual entitlement repair, absent invoices, unresolved refunds, settlement gaps, or support-only repair paths keep the pilot in preview. This protects the Rs. 100/month retail model from hidden operating costs and protects investors from confusing a successful checkout screen with real account entitlement.

Blocked data remains explicit: raw card data, UPI PIN or mandate credentials, bank login details, OTP, gateway secrets, PAN, folio, CAS, ARN/EUIN, distributor client records, and free-form private investment notes are outside the Phase 1 browser workflow. Paid features should unlock only from verified backend events and backend audit receipts.
